# Mutation uncertainty audit

This audit records how each Mutation that declares `uncertain`, or whose
unknown-outcome handling changed for issue #902, behaves in its Go code on
branch `connectors/unknown-outcome-retry` at `ec79a1668` (2026-11-18), after
the #902 review fixes, the pass that unified credential classification and
pre-write reads of `safe` operations, and the last-gaps pass. Every row was
re-verified against the code at that commit. The first table lists every Mutation that declares
`uncertain`, plus the operations in the same connectors that no longer declare
it or whose unknown-outcome handling changed. The second table lists Mutations
whose tier became `safe`, or whose safe-write handling changed, without an
`uncertain` branch. Each row states the tier and send cap, the read-back, how
resends are bounded, and exactly when `uncertain` is selected. Line links may
drift. The tiers and rules are defined in
[Repeat on an unknown outcome](connector-contract.md#repeat-on-an-unknown-outcome);
this page describes code, not provider behavior beyond it.

Shared behavior, not repeated per row:

- A definite refusal (HTTP 400, 401, 403, 404, 411, 413, 414, 415, or 422 with
  no acceptance in the body, or a documented provider error code) selects its
  branch on a first send and is never resent. After a possible earlier send,
  a refusal selects `uncertain` instead of `providerRejected` or `defect`.
- A transport failure before the request left the process, a 429, and a 503
  return Retry, unless a row says otherwise.
- A `limited` operation reads back first when it can and resends while
  `MaximumPriorSends + 1 < MaxSends`. "Fence `WithMaxSends(call.MaxSends())`"
  means the `sdkgo/singledispatch` bounded resend; a row names any other
  mechanism. Every `limited` operation here has the default `maxSends` 3, and
  an omitted tier is `limited`.
- A provider ID saved from an accepted answer is read back and never resent.
- Every connector classifies a credential failure the same way in Go, Python,
  and TypeScript, except that Go connectors have not yet adopted the SDK's
  `ErrCredentialMaterialInvalid` for malformed stored material (see
  [Open discrepancies](#open-discrepancies)). It is terminal only for
  reauthorization required (in Go, either `sdkgo.ErrReauthorizationRequired` or
  `projectconfig.ErrReauthorizationRequired`), a missing configuration object
  (`ErrObjectNotFound`), a connection the scope no longer selects
  (`ErrConnectionNotSelected`), a credential broker refusal
  (`ErrCredentialBrokerRejected`), and resolved credential material that fails
  a local validation or format check. Python and TypeScript test exactly
  those four classes, never a base class. Every other credential failure,
  including a broker outage, a timeout, a network error, a connection the
  static provider does not configure, and any unlisted error, returns Retry,
  recording `notSent` only before any possible send. A terminal failure
  selects the declared terminal branch (`defect`, or the row's credential
  branch) before any possible send, and `uncertain` after one on a `limited`
  or `unsafe` operation; a `safe` operation without `uncertain` keeps its
  declared branch or Retries as its row says. "Terminal credential failure"
  in a row means this set.
- Python and TypeScript ports were spot-checked against Go and match unless a
  row or [Language differences](#language-differences) says otherwise.

On attempt 2 or later every credential failure Retries; on the first, a terminal one selects `providerRejected` and invalid credential material `defect`. `invalidResponse` is never selected. |

## Deviations from the shared rules

These rows differ from the shared behavior above.

- `openai` `createResponse` retries a failed response-ID heartbeat write up to
  three times after a 2xx, then returns the paid Response even if all writes
  fail. If Dex also fails to commit Execute, a retry can lack the ID and create
  another billed Response within the limited-tier send cap. OpenAI has no
  create deduplication key or lookup by request ID to close this gap.

- 503 counts as a possible send, so it uses up the cap, in `google/gmail`
  `sendMessage` and `replyToMessage` (Sent Mail is searched, then the claim is
  kept) and in `notion` `createPage` when the 503 carries no
  `committed_resource_id`.
- `uncertain` can be selected below the cap in these cases, all after a
  possible earlier send unless noted: a refused lookup in `gorgias`; several
  matching tasks or comments in `clickup`; several envelopes carrying the
  marker, or a terminal session failure, in `docusign`; a definite refusal of
  the resend or the reply's source read, invalid input, a credential failure
  that needs reconnection, or a saved message ID that neither the ID read nor
  Sent Mail search confirms, in `google/gmail`; the cases its row
  lists in `microsoft/outlook-calendar` `createEvent`; a refused
  or invalid read-back, or an invalid part, in `intercom`; several matching
  messages in `microsoft/teams` channel and thread posts; duplicate key rows, a
  key or schema check that cannot run, or a saved append range whose row is
  still missing in `google/spreadsheet`; a read-back that cannot verify in
  `github`; a refused or invalid read-back, or a terminal credential failure, in
  `reamaze`; a non-retryable failure of the saved-ID read, the identity
  search, or the session start, or several identity matches, in `pipedrive`
  `upsertObject`; a transient read-back of an error-body ID whose checkpoint
  failed in `twilio/messaging` and `zoom`; a resend 3 hours 50 minutes or more
  after the first attempt, past WeCom's duplicate check, in `tencent/wecom`
  `sendApplicationMessage`; and, on any attempt, a Slack 409, an accepted
  answer without a usable ID (Slack, `helpscout`, `hiver`, `hootsuite`,
  `monday`, `notion`, `openai`, `telegram`, `tencent/wecom`,
  `twilio/messaging`, `wordpress`, `zoho/desk`, `zoom`, and others as their
  rows say), or an accepted answer whose one read-back fails
  (`atlassian/confluence`, `github`, `atlassian/jira` without a saved ID,
  `google/youtube` when its acceptance checkpoint also fails, `pipedrive`
  `upsertObject`).
- These operations reach `uncertain` one attempt after the capped send,
  because an unknown outcome always Retries and the next attempt reads back
  first: `atlassian/confluence` `addComment`, `gorgias`, `clickup`, `intercom`
  `replyToConversation`, `microsoft/excel` `appendTableRows`,
  `microsoft/teams` `postChannelMessage` and `postThreadReply`,
  `microsoft/outlook-mail`, `pipedrive` `upsertObject`, both `reamaze` writes,
  and `zendesk/support` `updateTicket`.
- Keyed `safe` writes select their refusal branch on any attempt instead of
  `uncertain`: `stripe` checkout sessions and `createRefund`, and `xero`. Both
  select `uncertain` instead for a credential refusal (`xero`) or a terminal
  credential or local failure on attempt 2 or later. `stripe` also selects
  `uncertain` for a replayed 5xx (for `createRefund`, after read-back finds no
  refund) and for an unusable 2xx, and `xero` for a 500, because each provider
  replays the same answer under the key. The keyed `safe` writes without
  `uncertain` (`resend` `sendEmail`, `klaviyo` `createEvent`, `mixpanel`
  `trackEvent`, `posthog` `captureEvent`, `linear`
  `createIssue` and `addComment`, and `snowflake` `submitStatement`) also
  select a definite refusal's branch on any attempt.
- `microsoft/entra-id` `createUser` and `addUserToGroup` repeat a definite
  400, and `addUserToGroup` a 404 while the group exists, within a one-minute
  directory propagation window. `microsoft/outlook-calendar` `createEvent`
  counts a transport error before dispatch as a send, which is conservative.
- `superdurable/oauth2-http` `sendRequest` is `safe` and selects `uncertain`
  only on attempt 2 or later, for a definite refusal of a write method or a
  terminal local failure.
- `front` `replyToConversation` Retries a reply read-back 404 instead of
  selecting `uncertain`, because a new message UID can lag; an internal note's
  404 still selects `uncertain`.
- `atlassian/jira-service-management` `transitionTicket` and `atlassian/jira`
  `transitionIssue` keep their own heartbeat checkpoint instead of a Fence, so
  a hand-written Step that also runs a fenced write would overwrite it; the
  generated Step factories run each in its own Step.

## Open discrepancies

- Packages that require a Connector SDK release older than the tier generate
  no `repeatOnUnknown`: 28 Go modules below `sdkgo` v0.37.0 (among them
  `stripe`, `box`, `dropbox`, `typeform`, `google/workspace-admin`,
  `google/cloud-storage`, `microsoft/entra-id`, `microsoft/onedrive`, and
  `amazon/s3`), and the `superdurable/webhook` Python and TypeScript packages,
  which pin Connector SDK 0.1.0. Every tier these manifests declare is
  `safe`, and the code behaves as `safe`.
- Several safe writes still select `invalidResponse` for an invalid read before
  the write, also on a repeat (`atlassian/jira-service-management`
  `updateTicket`, `intercom` `updateConversationState`, `google/docs`,
  `docusign` `voidEnvelope` on its account read, and `calendly`
  `createWebhookSubscription`, also after an unknown POST), and `amazon/sqs`
  `receiveMessages` selects it for an invalid or oversized 2xx on any attempt, while
  `freshworks/freshdesk`, `front`, `gorgias`, `helpscout`, `hiver`, `reamaze`,
  and `zoho/desk` Retry it.
- Several safe writes select `providerRejected` for a read status that is not
  a definite refusal, such as 3xx, 409, or an unlisted 4xx, also after a
  possible earlier write: the read before the write in `google/docs`,
  `intercom` `updateConversationState`, `atlassian/jira-service-management`
  `updateTicket`, `zoho/desk` `updateTicket`, and `calendly`
  `createWebhookSubscription` (408 included), the read-back in `clickup`
  `updateTaskTags` and `docusign` `voidEnvelope`, and the HEAD read-back after
  a create-only 412 in `amazon/s3` `putObject`. `google/workspace-admin`
  selects `providerRejected` for a 409 on its writes.
- `cloudflare` `purgeCacheByURLs` selects `providerRejected` for HTTP 200 with
  `success: false`; whether that is a definite provider refusal needs an owner
  decision. `amazon/sqs` `deleteMessage` can select `receiptHandleInvalid` on a
  repeat after a delete whose answer was lost (seen on ElasticMQ), while
  `changeMessageVisibility` guards that case on attempt 2 or later.
- `sdkgo/projectconfig` now returns `ErrCredentialMaterialInvalid` for a
  credential decoding failure without exposing decoder details. Go connectors
  still treat it as transient until they adopt the marker in a later release
  (#926); Python and TypeScript treat it as terminal through the generated
  `is_credential_material_error` and `isCredentialMaterialError`.
- A terminal credential failure after a possible send selects `defect` or
  `providerRejected` on any attempt in some `safe` rows (`airtable`,
  `clickup`, `calendly`, `docusign`, `helpscout`, `hubspot`, `intercom`,
  `intuit/mailchimp`, `pipedrive`, `salesforce`, `microsoft/outlook-mail`,
  `atlassian/jira-service-management` `updateTicket`, `google/calendar`,
  `google/cloud-storage`, and every `google/workspace-admin` and
  `microsoft/entra-id` Mutation) and only on the first
  attempt in others (`freshworks/freshdesk`, `front`, `gorgias`, `hiver`,
  `google/docs`, `reamaze`, `superdurable/email`, `zendesk/support`,
  `zoho/desk`, `box`, `dropbox`, `typeform`, `microsoft/onedrive`,
  `microsoft/outlook-calendar` `updateEvent`). `google/youtube`
  `addPlaylistItem` Retries invalid credential material after a possible
  insert instead of selecting `uncertain`.
- `atlassian/jira-service-management` `updateTicket` selects `notFound` or
  `providerRejected` for a definite refusal whose body is unreadable.
- `superdurable/email` `moveMessage` without `messageId` selects `notFound` on
  a repeat after an applied MOVE whose answer was lost.
- Several `uncertain` branch descriptions list fewer cases than the code
  selects: `intuit/quickbooks`, `hootsuite`, `meta/facebook-pages`, `notion`,
  `microsoft/outlook-mail`, `microsoft/outlook-calendar` `createEvent`,
  `monday`, `github`, `google/docs`, `google/drive`, `google/spreadsheet`, and
  `google/youtube`. None contradicts the code.
- Some `invalidResponse` descriptions do not yet say "no longer selected"
  although the code Retries instead: `google/workspace-admin`,
  `microsoft/entra-id`, `google/calendar`, and `zoho/crm`.

## Language differences

- `github` `createIssue` and `createIssueComment` have Go and TypeScript ports
  only; `tencent/wecom` is Go only.
- TypeScript computes the send cap as the manifest cap with the Step's
  `maxSendsOverride`, and 1 when the manifest cap is below 2. This matches
  `call.MaxSends()` in Go and `call.max_sends` in Python.
- Malformed stored credential material is terminal in Python and TypeScript
  and transient in Go; see [Open discrepancies](#open-discrepancies).
