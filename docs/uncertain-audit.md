# Mutation uncertainty audit

This audit records how each Mutation that declares `uncertain`, or whose
unknown-outcome handling changed for issue #902, behaves in its Go code on
branch `connectors/unknown-outcome-retry` at `8134164` (2026-11-17). 81 of the
179 Mutations declare `uncertain`; the first table lists them, plus four
operations that no longer do. The second table lists Mutations whose tier
became `safe`, or whose safe-write handling changed, without an `uncertain`
branch. Line links may drift. The tiers and rules are defined in
[Repeat on an unknown outcome](connector-contract.md#repeat-on-an-unknown-outcome);
this page describes code, not provider behavior beyond it.

Shared behavior, not repeated per row:

- A definite refusal (HTTP 400, 401, 403, 404, 411, 413, 414, 415, or 422 with
  no acceptance in the body, or a documented provider error code) selects its
  branch on a first send and is never resent. After a possible earlier send,
  a refusal selects `uncertain` instead of `providerRejected` or `defect`.
- A transport failure before the request left the process, a 429, and a 503
  return Retry, unless a row says otherwise.
- A `limited` operation reads back first when it can and resends while
  `MaximumPriorSends + 1 < MaxSends`. "Fence `WithMaxSends(call.MaxSends())`"
  means the `sdkgo/singledispatch` bounded resend; a row names any other
  mechanism. Every `limited` operation here has the default `maxSends` 3, and
  an omitted tier is `limited`.
- A provider ID saved from an accepted answer is read back and never resent.
- Python and TypeScript ports were spot-checked against Go and match unless a
  row or [Language differences](#language-differences) says otherwise.

## Deviations from the shared rules

These rows differ from the shared behavior above.

- 503 counts as a possible send, so it uses up the cap, in
  `atlassian/confluence` `addComment`, `docusign`
  `createEnvelopeFromTemplate`, and `google/youtube` `addPlaylistItem`.
- `uncertain` can be selected below the cap in these cases: a failed or
  refused lookup after a possible earlier send in `google/docs`,
  `google/spreadsheet`, `google/youtube`, and `pipedrive` `upsertObject`; a
  Slack 409, an unusable accepted answer, or a `FailClosed` decision once the
  attempt number reaches the cap.
- `stripe` checkout sessions are `safe` but select `uncertain` for a replayed
  5xx. `tencent/wecom` `sendApplicationMessage` selects `providerRejected` on
  any attempt, which its identical, deduplicated request makes harmless.
- `gorgias` reaches `uncertain` one attempt after the capped send, because an
  unknown outcome always Retries and the next attempt reads back first.

## Open discrepancies

- `doist/todoist` `updateTaskContent` and `superdurable/webhook` `sendEvent`
  omit the tier, so their generated definitions are `limited`, `maxSends` 3,
  while the code behaves as `safe`.
- The manifests of `google/docs` `createDocument`, `google/spreadsheet`
  `upsertRow`, and `google/youtube` `addPlaylistItem` say `uncertain` happens at
  the send cap; the code also selects it below the cap, as listed above.
- `superdurable/oauth2-http` `connector.yaml` line 124 says an unkeyed POST
  whose answer was lost selects `uncertain`; the code never selects it.
- `xero` `connector.yaml` line 31 says an oversized answer to an accepted write
  selects `uncertain`; the code Retries.
- `salesforce` `updateRecord` selects `providerRejected` for an HTTP 300; its
  README line 261 says a write's 3xx other than the upsert's 300 Retries.
- `atlassian/trello` `create_card.go` line 79 and `add_comment.go` line 62 say
  an ambiguous outcome does not resend; the code resends below the cap.

## Language differences

- `github` `createIssue` and `createIssueComment` have Go and TypeScript ports
  only; `tencent/wecom` is Go only.
- TypeScript computes the send cap as the manifest cap with the Step's
  `maxSendsOverride`, and 1 when the manifest cap is below 2. This matches
  `call.MaxSends()` in Go and `call.max_sends` in Python.
