# Braintree connector

Go implements `getTransaction`, `getCustomer`, `getPaymentMethod`, and `getRefund` by GraphQL ID using Braintree's [node query](https://developer.paypal.com/braintree/graphql/guides/node_query/). Python and TypeScript implement `getTransaction` only. A null node, a node of another type, or only `NOT_FOUND` GraphQL errors select optional `notFound`. GraphQL errors with [`errorClass`](https://developer.paypal.com/braintree/graphql/guides/making_api_calls/) `INTERNAL`, `SERVICE_AVAILABILITY`, or `RESOURCE_LIMIT` retry; any other GraphQL error class selects `providerRejected`. HTTP 429, server failures, and transport failures retry. The read operations never move money.

## Connection and configuration

Open the matching [Braintree sandbox or production Control Panel](https://developer.paypal.com/braintree/articles/control-panel/important-gateway-credentials), then **gear icon > API > API Keys**. Generate an API key if necessary. Copy its Public Key into `publicKey`, select **View** in the Private Key column, and copy the secret into `privateKey` in Dex Web Connections. Both are required and must come from the same environment. Dex sends their Basic encoding only in the provider request. Never enter a tokenization key or a merchant ID in these fields.

Leave `baseUrl` blank for the sandbox GraphQL root. For production, enter `https://payments.braintree-api.com`. Leave `apiVersion`, `timeout`, and `maxResponseBytes` blank for their displayed defaults. The [Braintree GraphQL request guide](https://developer.paypal.com/braintree/graphql/guides/making_api_calls/) specifies the API version date and request headers. Pass a GraphQL resource ID in the corresponding operation input; blank is invalid. A legacy SDK ID may not be the same value.

Runnable examples are in [`go/examples/transaction-read`](go/examples/transaction-read), [`python/examples/transaction_read`](python/examples/transaction_read), and [`typescript/examples/transaction-read`](typescript/examples/transaction-read). Provider conformance scenarios are recorded from Go and replayed by Python and TypeScript. Live Braintree authorization and provider behavior require user-controlled sandbox or production keys and remain unverified here.

Go customer writes follow Braintree's [customer guide](https://developer.paypal.com/braintree/graphql/guides/customers). `createCustomer` accepts contact fields and uses a limited send cap because Braintree's `clientMutationId` correlates responses but does not deduplicate creations. `updateCustomer` sends absolute contact field values and is repeat safe; blank clears a field. `deleteCustomer` removes a customer only after vaulted payment methods are deleted, and breaks association with earlier transactions. The [Go Flow example](go/examples/transaction-read/README.md) creates a customer through a mock backed by real Dex; live provider behavior remains unverified.

Payment method writes follow the [payment method guide](https://developer.paypal.com/braintree/graphql/guides/payment_methods/). `vaultPaymentMethod` consumes a client-tokenized single-use ID and returns a multi-use ID; never put raw card data in Flow inputs. The three credit card update operations replace cardholder name, expiration date, or billing address. Vaulting and updates use a limited send cap because repeated requests can repeat verification, and `clientMutationId` is not a provider deduplication key. `deletePaymentMethodFromVault` removes a multi-use method; for Venmo it may also disconnect the merchant. The Go example vaults a payment method against a mock-backed real Dex Flow. Live provider authorization, card verification, and deletion effects remain unverified.

Transactions follow the [transaction guide](https://developer.paypal.com/braintree/graphql/guides/transactions/). `searchTransactions` reads one page by exact transaction ID or order ID. `chargePaymentMethod` captures funds immediately, `captureTransaction` captures an existing authorization, `voidTransaction` cancels an unsettled payment, and `refundTransaction` returns funds on an eligible settled payment. Each financial Mutation sends Braintree's documented `apiRequestKey` from the stable Dex call identity and repeats safely within the one-hour retry budget; the provider key expires after 30 days. Recorded conformance checks the same key on a 500 then success sequence. Amounts are positive decimal strings in the merchant account currency; a blank capture or refund amount means the full eligible amount. The Go example charges a mock-backed payment method through real Dex. Live money movement, provider permissions, and status transitions remain unverified.

Disputes follow Braintree's [dispute management guide](https://developer.paypal.com/braintree/docs/guides/disputes/managing/). `getDispute` reads status, reply-by date, and evidence; `searchDisputes` returns one page by exact ID or status. `acceptDispute` accepts an open case and may return funds to the customer. `createDisputeTextEvidence` attaches a categorized statement; `deleteDisputeEvidence` removes an attachment; `finalizeDispute` submits the case and evidence before its deadline. Braintree has no dispute `apiRequestKey`, so the three potentially repeated actions use a bounded send count and read the dispute before resending after an unknown outcome. File evidence requires a separate multipart upload and is not implemented in this slice. The Go example accepts a mock-backed dispute through real Dex; live dispute permissions and bank submission remain unverified.
