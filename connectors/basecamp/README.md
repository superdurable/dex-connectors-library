# Basecamp connector

Go implements `listAccounts`, `listProjects`, `getProject`, `createProject`, `updateProject`, `archiveProject`, `unarchiveProject`, `trashProject`, `listTodos`, `getTodo`, `createTodo`, `updateTodo`, `completeTodo`, `uncompleteTodo`, `trashTodo`, and `repositionTodo`, `listTodoLists`, `getTodoList`, `createTodoList`, `updateTodoList`, `repositionTodoList`, and `trashTodoList`, `listPeople`, `listProjectPeople`, `getPerson`, `grantProjectAccess`, `revokeProjectAccess`, and `enrollPerson`, `listMessages`, `getMessage`, `createMessage`, `updateMessage`, `publishMessage`, `pinMessage`, `unpinMessage`, and `trashMessage`. [Python](python/README.md) and [TypeScript](typescript/README.md) implement `listAccounts` only. The account Query reads Basecamp's [authorization document](https://github.com/basecamp/bc-api/blob/master/sections/authentication.md#get-authorization), keeps only `bc3` account IDs and names, and omits the identity profile. Go resource Queries use the [Basecamp 3 API](https://github.com/basecamp/bc-api) with numeric account and resource IDs. The runnable [Go](go/examples/accounts/README.md), [Python](python/examples/accounts/README.md), and [TypeScript](typescript/examples/accounts/README.md) Flows use the static `basecamp` Dex Web connection.

At [Launchpad Integrations](https://launchpad.37signals.com/integrations), register an application and the exact redirect URL from Dex Web. Save its Client ID and secret in Dex, then authorize an identity with the desired Basecamp accounts. Dex refreshes the Bearer token; token values stay outside Flow state. Launchpad uses account consent and may ignore the requested `read` scope.

`listAccounts` accepts an optional zero-based offset and a local limit from 1 through 100; an omitted or zero offset starts at the first account, and an omitted or zero limit uses 100. The provider returns its accessible accounts in one response, so the connector bounds the response in bytes before slicing it. It retries HTTP 429, timeouts, transport failures, and server errors. Live provider authorization and Dex Web rendering remain unverified.

The Go project and to-do Queries read one provider page at a time. `listProjects` returns active projects, and `listTodos` returns pending to-dos. Obtain the account ID from `listAccounts`; use project and to-do list IDs from Basecamp results. The connector validates IDs before building URLs and treats 404 on singular reads as `notFound`. These reads are safe to repeat.

Project writes follow Basecamp's [project API](https://github.com/basecamp/bc-api/blob/master/sections/projects.md). `createProject` uses a bounded limited send tier because Basecamp does not accept a project idempotency key; if the cap is reached without a stable confirmation, the outcome is `uncertain`. `updateProject` replaces the name and description; blank description clears it. `archiveProject`, `unarchiveProject`, and `trashProject` are repeat-safe status changes. Trashing can be permanent on plans that do not support archiving. The [Go example](go/examples/accounts/README.md) includes a project creation Flow. List pagination beyond the first page and live provider behavior remain unverified.

To-do writes follow the [to-do API](https://github.com/basecamp/bc-api/blob/master/sections/todos.md) and [recording trash API](https://github.com/basecamp/bc-api/blob/master/sections/recordings.md#trash-a-recording). `createTodo` uses the limited tier because Basecamp has no to-do idempotency key or unique lookup key. `updateTodo` sends a complete replacement of title, rich text description, dates, assignees, and completion subscribers; obtain the current values from `getTodo` and supply explicit empty lists when clearing assignments. `completeTodo`, `uncompleteTodo`, `trashTodo`, and `repositionTodo` are repeat-safe state changes. Position is one-based and the optional parent must be a list or to-do set in the same project. The Go example includes a to-do creation Flow; no real Basecamp authorization was available for live verification.

To-do lists follow the [to-do list API](https://github.com/basecamp/bc-api/blob/master/sections/todolists.md). `getProject` exposes the to-do set ID from its dock, which `listTodoLists` and `createTodoList` use. `createTodoList` is limited because Basecamp does not deduplicate list creates; `updateTodoList`, `repositionTodoList`, and `trashTodoList` are safe absolute changes. A blank description clears it on update. The list and to-do list Queries currently return only the first provider page.

People follow the [people API](https://github.com/basecamp/bc-api/blob/master/sections/people.md). `listPeople` reads account people, `listProjectPeople` reads active project members, and `getPerson` reads one profile. `grantProjectAccess` and `revokeProjectAccess` use repeat-safe membership changes for existing people. `enrollPerson` creates or re-enrolls one account person by email, can grant visible projects, and uses the limited tier because repeated sends may send another invitation. Basecamp may redact email addresses for non-admin callers. The current Basecamp 5 API does not expose a person delete or arbitrary profile update operation; only the authenticated person's own profile can be updated.

Messages follow the [message API](https://github.com/basecamp/bc-api/blob/master/sections/messages.md). `getProject` exposes its message board ID; `listMessages` reads one active page and `getMessage` reads one post. `createMessage` defaults to an unpublished draft, or posts immediately with `Publish: true`; it uses the limited tier because a repeated create can post or notify twice. An omitted subscriber list uses Basecamp's all-project default, while an explicit empty list suppresses subscribers. `updateMessage` merges a replacement subject and content, `publishMessage` publishes a draft with Basecamp's once-only notification behavior, and `pinMessage`, `unpinMessage`, and `trashMessage` apply repeat-safe state changes.
