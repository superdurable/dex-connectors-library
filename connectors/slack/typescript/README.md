# Slack TypeScript connector

Install `@superdurable/connector-slack@0.8.0` with `@superdurable/connectors-sdk@0.11.0` and `@superdurable/dex` 1.28 or newer. This package implements every Go operation, `listChannels`, `getWorkspaceIdentity`, `listThreadMessages`, `getThreadReply`, `listChannelMessages`, `postChannelMessage`, `postThreadReply`, and `postButtonMessage`, and every Go Trigger, `channelThreadCreated`, `threadReplyCreated`, and `buttonClicked`.

Use `newProjectConnection(project, 'slack-thread-reader')` with a Dex project loaded by `loadFromEnvironment`. The project credential source refreshes the OAuth bot and user tokens using generated manifest declarations. Bot credentials send messages, list channels, read channel history, and read the workspace identity; user credentials read thread replies. The package does not place credentials in Flow state.

The runnable [thread page example](examples/list-thread-messages/README.md) and [channel history example](examples/list-channel-messages/README.md) are the minimal consuming applications and show the static connection name, Worker entrypoint, and Flow Definition Graph 2.0 source. The provider replay tests cover each operation against Go-recorded requests and decisions. Live Slack OAuth and provider behavior have not been verified for this package.

## Buttons

From 0.7.0, `postButtonMessage` posts one message whose text appears in a Block Kit section above 1 through 25 buttons, as a top-level message or, with `threadTimestamp`, as a thread reply, at parity with Go. Each button has a required `actionId`, unique in the message and at most 255 characters; a required plain-text `text` label of at most 75 characters; an optional `value` of at most 2000 characters that the click returns unchanged; and an optional `style` of `ButtonStylePrimary` or `ButtonStyleDanger`. The message text is also the notification fallback and must be at most 3000 characters. `validatePostButtonMessageInput` names the first broken limit; invalid input selects `defect` before anything is sent. The post uses `chat.postMessage` with the existing `chat:write` scope and the same single-dispatch fence, retry policy, read-back, and branches as `postThreadReply`, and replays the Go-recorded conformance scenarios. A button value is visible to every member who can see the message and is recorded in the durable inbox, so it must never contain a secret.

The `buttonClicked` Trigger delivers a `ButtonClickEvent` for each click on a button in its channel: team, channel, message timestamp, thread timestamp (the message's own timestamp for a top-level message), clicker user ID, action ID, value, and action timestamp. Its configuration takes the required `channelId`, optional `actionIds`, and optional `clickerUserIds`; an empty list matches everyone. The event ID joins the team, channel, message timestamp, action ID, and action timestamp, so each click is a separate event and a replayed click deduplicates. Events and records never carry the payload's response URL, trigger ID, or verification token, and records never carry the button value.

- Add `buttonClickedRoutes` to the one `newProjectMessageTriggerRunner` of the connection, beside its message routes, since Slack sends each envelope to only one of an app's connections. The runner acknowledges a click once its durable inbox recorded it, delivers acknowledged events in arrival order separately, and logs WARN `slack interactive envelope acknowledged late` with `elapsed_ms` when recording took longer than Slack's three seconds.
- Button routes require durable inboxes: `newMessageTriggerRunner` with button routes throws unless every route's target, message routes included, comes from `newDurableTriggerTarget`, and `newButtonClickedTrigger`, whose runner cannot pass a durable inbox to its source, always rejects from `run`.
- Clicks reach only Socket Mode. On a relayed connection without an `app_token`, `run` of a runner with button routes rejects.
- `defineButtonClickedTriggerBinding` declares the static binding and its configuration units for Dex Web.

The runnable [button approval example](examples/button-approval/README.md) replies to a request with Approve and Reject buttons and completes on the first decider's click; its integration test runs on a real Dex Worker and Client. Live Slack Interactivity delivery and Slack's rendering of the buttons have not been verified for this package.

Every query checks the HTTP status before decoding the body: HTTP 429 and 5xx return Retry and honor `Retry-After`, even when Slack sends no JSON body. From 0.4.1 this includes `listThreadMessages` and `getThreadReply`. From 0.5.0, `listChannelMessages` reads one newest-first page of a channel's top-level messages from `conversations.history` with the bot token; `pageSize` is 1 through 15 (blank or 0 reads 15).

From 0.8.0, `postChannelMessage`, `postThreadReply`, and `postButtonMessage` resend a post whose outcome is unknown, at parity with Go v1.8.0. A connection loss after dispatch, other 5xx, or an `internal_error` or `fatal_error` without a timestamp returns Retry, and the next attempt resends with the same `client_msg_id`, because a lost timestamp cannot be read back. Each Step call sends at most `maxSends` times, 3 from the generated definition; the next unknown outcome at that cap selects `uncertain`. A Step factory's `maxSends` option changes the cap from 1 (never resend) to 10. A checkpointed timestamp is read back and never resent, and a 409 or an accepted post without a usable identity still selects `uncertain` without a resend, because Slack accepted the post and a resend would certainly duplicate it. Definite refusals are never resent: a refusal of a first send selects `providerRejected`, and a refusal of a resend selects `uncertain`, because an earlier send may have posted. Slack's `client_msg_id` deduplication is unverified, so a resend may post a duplicate. See the [connector guide](../README.md#operations).

## Triggers

From 0.6.0, `channelThreadCreated` receives a matching top-level message and `threadReplyCreated` a matching thread reply, at parity with the Go connector. The runnable [thread approval example](examples/thread-approval/README.md) starts a Flow from a root message, approves it from a reply through a typed RPC, and posts a completion reply.

- `newProjectMessageTriggerRunner(project, connectionName, { channelThreadCreatedRoutes, threadReplyCreatedRoutes })` runs every binding of one connection on one runner, because Slack sends each event to only one of an app's Socket Mode connections. Each route's target receives its events through the binding's durable project inbox. Wire targets with `newDexFlowTriggerTarget` and `newDexRPCTriggerTarget` from `@superdurable/connectors-sdk`.
- The runner reads the connection's credential once. With an `app_token` it uses Socket Mode: it acknowledges each envelope after the matching inboxes recorded it, reconnects with a doubling delay from 1 to 30 seconds, and treats 45 seconds without an envelope or ping as a dead connection. Without one, on a shared connection, it serves the Events API callbacks its host relays: mount `runner.serveHTTP` at `relayedTriggerPath(connectionName)`, which is `/triggers/slack/` and the unpadded base64url connection name. The runner registers that route at the host's `/internal/slack-triggers/register` and verifies each callback's `Dex-Relay-Signature` with the scope token within a five-minute window, without reading a Slack credential.
- A root message is delivered before any reply received after it. Bot messages, edited or other subtype messages, and messages without a user are ignored; ignored messages are logged at DEBUG with their reason and never their text.
- `defineChannelThreadCreatedTriggerBinding` and `defineThreadReplyCreatedTriggerBinding` declare static bindings and their configuration units for Dex Web.

Socket Mode, relay registration, signature checks, ordering, and the real Dex example are tested against local stand-ins for Slack and the host. Live Slack Socket Mode and a live host relay have not been verified for this package.
