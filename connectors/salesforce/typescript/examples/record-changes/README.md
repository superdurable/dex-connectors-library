# Salesforce record changes Flow

This example polls one Salesforce object with the `recordModifiedPolled` Trigger and starts one `SalesforceRecordChangeTypeScript` Flow per created or modified record. The Flow records the delivered change, reads the record back with `getRecord` for every field the change carries, and completes with its current values; a record deleted before the read-back takes the wired `notFound` branch and completes as deleted. `main.ts` is the Worker entrypoint; `app.ts` runs the Worker and the durable poll runner on one event loop.

Configure the static `salesforce-crm` connection in Dex Web **Connections** with the Salesforce OAuth guide in the [connector README](../../../README.md#authorization); the record-lookup example uses the same connection. Optionally set **Poll interval** (`pollInterval`, at least 5s; every poll spends one request of the org's 24-hour API allocation, shown at Setup > Company Information > API Requests, Last 24 Hours) and **Poll page size** (`pollPageSize`, the SOQL `LIMIT` of one poll request, 1 to 500). Then save the `record-changes` Trigger binding's **Watched object** (`sObjectPicker`, required: a standard object, or a custom object API name from Setup > Object Manager > the object > API Name, such as `Invoice__c`) and, optionally, **Delivered fields** (`fieldNamesInput`: up to 50 field API names from Setup > Object Manager > the object > Fields & Relationships > Field Name, such as `Name, StageName`; blank delivers only `Id`, `CreatedDate`, `LastModifiedDate`, and `SystemModstamp`). The connected user needs read access to the object and every listed field. The first start records existing records as a baseline and starts no Flow for them. Restart the Worker after saving; a changed object records a new baseline, and a changed field list keeps the cursor.

From `connectors/salesforce/typescript`, run `npm ci`, then `npm run example:changes`. Set `DEX_FLOW_SERVICE_ADDRESS` for a nondefault Dex endpoint and `LOG_LEVEL=debug` to see every poll and delivery. Each change is recorded in the binding's project Trigger inbox before the cursor commits, so a restart neither misses nor repeats a change, and the Flow ID `salesforce-record-change-<event ID>` keeps a redelivered change to one Flow. Under `dexcli dev` the poll cursor stays in process memory, so a restarted local Worker records a new baseline.

`npm run test:integration` runs `test/integration/record-changes.integration.test.ts` against a running `dexcli dev` and an in-process stand-in for the REST query and sObject Rows resources: existing records stay a baseline, each change starts exactly one Flow, a bulk load sharing one `SystemModstamp` pages by `Id`, a `REQUEST_LIMIT_EXCEEDED` pause loses nothing, a record deleted before the read-back completes as deleted, changes made while the process is stopped arrive after a restart, and changing the object records a new baseline. `test/record_changes_workflow.test.ts` covers the mappers, the binding's two units, and binding validation without Dex. `dexcli visualize --schema-version 2.0 examples/record-changes/flow/workflow.ts` reads the Flow and its binding once the package resolves from `node_modules`. Live Salesforce polling has not been verified.
