# Adobe Acrobat Sign connector

The Go, Python, and TypeScript `getAgreement` Queries read an agreement's ID, name, and status from Acrobat Sign REST API v6. Go also offers `listAgreements` for cursor pages, `updateAgreementVisibility` to set SHOW or HIDE for the calling user's agreement list, and `cancelAgreement` to transition an active agreement to CANCELLED. These operations exclude participant identities and document contents from Dex results.

## Connection

In an Acrobat Sign Enterprise account, open **Acrobat Sign API > API Information > Integration Key** and create an integration key with the `agreement_read` scope. Add `agreement_write` if the connection will call `updateAgreementVisibility` or `cancelAgreement`; an existing read-only key continues to work for reads. If Integration Key is unavailable, request enablement from Acrobat Sign support. Open **Personal Preferences > Access Tokens**, select the key, reveal its Integration Key value, and store it in the Dex Web connection's secret `integration_key` field. Do not enter the key in a Flow input. See Adobe's [integration key setup](https://helpx.adobe.com/sg/sign/web/integrations/integration-keys/create.html), [key retrieval](https://helpx.adobe.com/my_en/sign/web/integrations/integration-keys/retrieve.html), and [official API schema](https://github.com/adobe-sign/AdobeSign-OpenAPI/blob/master/json/agreements.json).

Leave `baseUrl` blank for the displayed commercial discovery endpoint. The connector calls `baseUris` to resolve the account's regional `apiAccessPoint`, validates it, and caches it for that integration key before reading the agreement. `timeout` is a per-request Go duration; `maxResponseBytes` is a byte limit. Leave both blank for their displayed defaults. The query input `agreementId` is the non-secret ID returned by Acrobat Sign when an agreement is created. See Adobe's [API getting started](https://experienceleague.adobe.com/en/docs/acrobat-services-learn/tutorials/acrobatsign/signapi) and [agreement API](https://developer.adobe.com/acrobat-sign/docs/overview/developer_guide/apiusage).

## Example and verification

Run the [Go](go/examples/agreement-inspection/README.md), [Python](python/examples/agreement_inspection/README.md), or [TypeScript](typescript/examples/agreement-inspection/README.md) agreement inspection Flow with a static `adobe-acrobat-sign` connection. The Go Worker also registers `AdobeAcrobatSignAgreementList`; its mock integration test runs against real Dex. Go-recorded conformance covers the Go operations, while Python and TypeScript replay only their declared `getAgreement` capability. A real Adobe authorization, agreement read, or visibility write has not been verified locally.

`listAgreements` accepts an optional opaque `cursor` from `nextCursor` and a `pageSize` from 1 to 100; blank cursor and zero size use the provider's first page and default size. `updateAgreementVisibility` accepts an agreement ID and `SHOW` or `HIDE`. It uses `repeatOnUnknown: safe` because repeated writes set the same absolute visibility; the operation does not delete document content. `cancelAgreement` reads the current status before PUT /state and treats ABORTED as already cancelled; it is safe to repeat. Creation and sending need document and recipient handling and can produce duplicate legal agreements without a provider idempotency key. Reminders can duplicate recipient email, and document downloads are binary streams. Those operations remain outside this metadata connector.
