# WhatsApp Business Platform connector

The Go connector implements `listPhoneNumbers`, `sendTextMessage`, and `sendTemplateMessage`. The [phone-number inspection](go/examples/phone-numbers/README.md), [text send](go/examples/text-message/README.md), and [template send](go/examples/template-message/README.md) Flows are runnable consumers. The [Python](python/README.md) and [TypeScript](typescript/README.md) packages replay the Go scenarios and include three runnable Dex Flows each. Webhook reception remains unimplemented.

Create a Meta business portfolio, WhatsApp Business Account (WABA), business phone number, and Meta app. In [Meta Business Settings](https://business.facebook.com/settings/system-users), assign the WABA to a system user and generate a secret access token with `whatsapp_business_management` and `whatsapp_business_messaging`. Save it only in the Dex connection. Find the numeric WABA ID under Business Settings > Accounts > WhatsApp Accounts; `listPhoneNumbers` returns the sender `phoneNumberId`. The connector uses the versioned Graph API endpoint from the manifest. Meta's [official Cloud API collection](https://www.postman.com/meta/whatsapp-business-platform/documentation/wlk6lh4/whatsapp-cloud-api) documents token permissions and API requests.

Use `sendTextMessage` only inside Meta's customer service window. To start or resume a conversation, create an approved template in WhatsApp Manager and call `sendTemplateMessage` with its exact name and language code. Both sends accept a recipient in E.164 digits without `+`. The template operation supports text body placeholders through `bodyParameters` in order; other component types are not yet supported. A `sent` result confirms Meta returned a message ID, not that the recipient received the message. Meta's [business messaging policy](https://whatsappbusiness.com/policy/) explains the window and template requirements.

The [Go-recorded provider scenarios](../../../conformance/connectors/meta/whatsapp-business/scenarios.json) cover each operation branch, retry, and uncertain send outcome. Queries retry transient failures. Sends retry without counting a send when dispatch definitely did not start or Meta returned HTTP 429, 503, or a Graph throttling code. The Cloud API has no send idempotency key or read-back, so an unknown outcome (a 5xx other than 503, 408, 409, any 4xx other than 400, 401, 403, 404, 411, 413, 414, 415, or 422, an interrupted or malformed response, or a connection lost after dispatch) resends while possible sends stay below the operation's `maxSends` (default 3), so the customer may receive a duplicate, and selects `uncertain` at the cap; do not resend it blindly. A definite refusal selects `providerRejected` and is never resent; after an earlier possible send it selects `uncertain`. A wamid checkpointed by an earlier attempt completes the Step without resending, and a response with a wamid but an incomplete envelope selects `uncertain`. An unreadable checkpoint retries without sending. Unwired optional branches fail the Flow. Provider message bodies, token values, and phone numbers are not copied to failure messages. Live Meta authorization and Dex Web setup have not been exercised.
