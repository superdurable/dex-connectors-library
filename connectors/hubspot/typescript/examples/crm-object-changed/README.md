# CRM object changed Flow

This example polls one HubSpot object type with the `crmObjectChanged` Trigger and starts one `HubSpotCRMObjectChangeTypeScript` Flow per created or changed record. The Flow records the delivered change, reads the record back with `getObject`, and completes with its current values. `main.ts` is the Worker entrypoint; `app.ts` runs the Worker and the durable poll runner on one event loop.

Create the static `hubspot-crm-watcher` connection in Dex Web **Connections** with a private app token or OAuth, as described in the [package README](../../README.md). The app needs the `crm.objects.<type>.read` scope of the watched type, which the authorization guide lists. Optionally set `pollInterval`, the delay between polls (at least 5s). Then open the Flow's `crm-object-changes` Trigger binding and pick the **Watched object type**. The first start records existing records as a baseline and starts no Flow for them; restart the Worker after changing the type, which records a new baseline.

From `connectors/hubspot/typescript`, run `npm ci`, then `npm run example:changes`. Set `DEX_FLOW_SERVICE_ADDRESS` for a nondefault Dex endpoint and `LOG_LEVEL=debug` to see every poll and delivery. Each change is recorded in the binding's project Trigger inbox before the search cursor commits, so a restart neither misses nor repeats a change, and the Flow ID `hubspot-crm-object-change-<event ID>` keeps a redelivered change to one Flow.

`npm run test:integration` runs `test/integration/crm-object-changed.integration.test.ts` against a running `dexcli dev` and a local HubSpot search stand-in: existing records stay a baseline, each change starts exactly one Flow, changes made while the process is stopped arrive after a restart, and a 429 with `Retry-After` pauses polling before the change is delivered. `test/crm_object_changed_workflow.test.ts` covers the mappers, the binding's picker unit, and binding validation without Dex.
