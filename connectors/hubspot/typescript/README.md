# HubSpot TypeScript connector

`@superdurable/connector-hubspot` provides Dex Steps for `searchObjects`, `getObject`, `upsertObject`, and `updateObject`, and, from 0.2.0, the `crmObjectChanged` poll Trigger at parity with the Go connector. It requires `@superdurable/connectors-sdk` 0.12.0 and `@superdurable/dex` 1.45.4 or newer. It supports HubSpot private app tokens and HubSpot OAuth. The connection resolves credentials at dispatch, refreshes OAuth tokens through the generated manifest driver, and retries one request after a rejected OAuth access token. The two writes are repeat-safe: upsert uses a unique HubSpot property and update replaces named property values. From 0.2.1 both declare `repeatOnUnknown: safe` and retry any HTTP status that does not prove a refusal, including a lasting `409` to an upsert; an update still selects `conflict` for `409`.

The [search deals example](examples/search-deals/README.md) is a runnable Flow with a Worker entrypoint and static `hubspot-crm` connection name. Create that connection in Dex Web **Connections**. For private apps, open [HubSpot](https://app.hubspot.com/), choose **Development > Legacy apps > Create legacy app > Private**, grant the CRM read and write scopes listed in `connector.yaml`, and copy the access token from the app's **Auth** tab. For OAuth, choose a public legacy app or project app, register the redirect URI shown in Dex Web on the app's **Auth** tab, add the manifest scopes, enter the client ID and secret, and complete consent. Dex Web holds the credentials; they never enter Flow input or output.

From this directory, run `npm ci`, `npm run check`, `npm run example:search`, and `npm run example:changes`. To submit the sample input, run `npm run example:search:start -- examples/search-deals/input.example.json` in another terminal. Set `DEX_FLOW_SERVICE_ADDRESS` when Dex uses a nondefault port. `npm run test:integration` runs the same Flow through a real Dex Worker and Client against a local provider stand-in.

The package exports generated Config, Credentials, operation models, definitions, Step factories, and mock cases. Use `newProjectConnection(project, ConnectionName)` to bind the project connection, or `newConnection(new HubSpotClient(config, credentialSource), reference)` when constructing a client directly. The provider endpoint defaults to HubSpot's public API; `maxResponseBytes` defaults to one MiB; `pollIntervalMs` defaults to 30 seconds and must be at least 5 seconds. A project connection reads the saved `pollInterval` as Go `time.Duration` nanoseconds.

## crmObjectChanged Trigger

`crmObjectChanged` polls one object type, `contacts`, `companies`, or `deals`, through HubSpot CRM search and delivers one `CRMObjectChangedEvent` per created or changed record: `objectType`, `changeKind` (`created` or `updated`), `modifiedAt`, and the `object` as search returned it. It is built on the `@superdurable/connectors-sdk/pollingtrigger` kit and follows the Go connector exactly: the first poll records the newest last-modified date as a baseline and delivers no existing record; later polls search ascending on `lastmodifieddate` (contacts) or `hs_lastmodifieddate`, 100 records per page, re-read a two-minute lag window for late-indexed records, and skip versions already delivered. A 429 or 423 pauses every binding of the connection for `Retry-After` or `X-HubSpot-RateLimit-Interval-Milliseconds`, an exhausted daily limit backs off up to 15 minutes, and a rejected paging offset or unusable cursor records a new baseline with a WARN record. The [connector README](../README.md#crmobjectchanged-trigger) describes the behavior in full.

The cursor document is the Go connector's JSON byte for byte, and the event ID is the same hash of object type, record ID, and last-modified millisecond, so Go and TypeScript replicas can share one binding's cursor and inbox. A test replays a scenario recorded from the Go fetcher (`test/fixtures/go-crm-object-change-cursors.json`) and compares every cursor token and event ID.

`newProjectCRMObjectTriggerRunner(project, connectionName, { crmObjectChangedRoutes }, options)` is the durable path: it loads each binding's saved object type, records every change in the binding's project Trigger inbox, and commits the search position in its project poll cursor only after that. From [`examples/crm-object-changed/app.ts`](examples/crm-object-changed/app.ts):

```ts
const runner = newProjectCRMObjectTriggerRunner(project, ConnectionName, { crmObjectChangedRoutes: [{
  bindingName: CRMObjectChangedTriggerBinding, properties: DeliveredProperties,
  target: newDexFlowTriggerTarget(client, flow, acceptEveryCRMObjectChange, resolveFlowId, mapToFlowInput, { logger: options.logger }),
}] }, hubspotOptions);
```

Run it with `runner.run(newTriggerContext(signal))`; `runner.wakePoller(bindingName)` polls a binding at once. `newCRMObjectTriggerRunner` takes targets and cursor stores directly, and `newCRMObjectChangedTrigger` builds one binding for `newTrigger`; both keep the cursor in memory unless given a store, so a restart records a new baseline. `defineCRMObjectChangedTriggerBinding` declares a Flow's static binding with the `objectTypePicker` unit (`UIUnitObjectTypePicker`, port `objectType`). The `logger` client option receives seed, reseed, failure, pause, and inbox records, which never contain record properties or credentials.

The [crm-object-changed example](examples/crm-object-changed/README.md) starts one Flow per change. `npm run test:integration` runs it on a real Dex Worker and Client against a local HubSpot search stand-in, covering the baseline, one Flow per change, changes made while the process was stopped, and a 429 pause. Live HubSpot search has not been verified.
