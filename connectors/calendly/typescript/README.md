# Calendly TypeScript connector

Install `@superdurable/connector-calendly@0.2.1` with `@superdurable/connectors-sdk@0.11.0` and `@superdurable/dex` 1.45.4 or newer, which that SDK release requires. The package implements `listScheduledEvents`, `getScheduledEvent`, `listEventInvitees`, `cancelScheduledEvent`, `createSchedulingLink`, and `createWebhookSubscription` for Dex Flows, and from 0.2.0 the signed `inviteeEventReceived` Trigger.

From 0.2.1, `createSchedulingLink` resends an unknown outcome, such as a lost answer, `5xx`, or `409`, while possible sends stay below the Step's send cap and selects `uncertain` at the cap; an unreadable dispatch checkpoint returns Retry. `cancelScheduledEvent` and `createWebhookSubscription` declare `repeatOnUnknown: safe` and retry any answer Calendly did not definitely refuse.

Configure the `calendly-scheduling` example connection in Dex Web. A personal access token comes from [Calendly Integrations > API & Webhooks](https://calendly.com/integrations/api_webhooks). For OAuth, create a Web app at the [Calendly developer console](https://developer.calendly.com/console/apps), register Dex Web's displayed redirect URI, and enable `users:read`, `event_types:read`, `scheduled_events:write`, `scheduling_links:write`, and `webhooks:write`. Dex holds the token, client secret, and refresh token in the connection; the generated project credential provider rotates OAuth credentials before use. The `webhook_signing_key` is needed only to create a subscription with a personal access token and to verify deliveries in an `inviteeEventReceived` application.

With `dexcli dev` running, use `npm run example:event` for the [Worker](examples/scheduled-event/main.ts), then `npm run example:event:start -- examples/scheduled-event/input.example.json` to start one Flow. Set `DEX_FLOW_SERVICE_ADDRESS` if Dex runs on a different address. The Flow stores only the provider-safe scheduled event. The example has a real Dex Worker and Client integration test with a local Calendly stand-in.

## Triggers

From 0.2.0, `inviteeEventReceived` receives Calendly's signed `invitee.created` and `invitee.canceled` webhooks at parity with the Go connector. The runnable [invitee-recorder example](examples/invitee-recorder/README.md) starts one Flow per booked invitee and reads its scheduled event back.

- `newProjectInviteeEventReceivedEndpointRunner(project, connectionName, routes)` opens the connection and every route's binding from the loaded project and wraps each target in the binding's durable project inbox, so a delivery is stored before Calendly receives `200`. Mount `runner.serveHTTP` at the subscription's callback URL, run `runner.run(context)` for the life of the process, and use `runner.runningSourceCount()` as readiness. Wire targets with `newDexFlowTriggerTarget` from `@superdurable/connectors-sdk`.
- The endpoint verifies `Calendly-Webhook-Signature` (`t=<unix seconds>,v1=<hex HMAC-SHA256 of "t.body">`) with the connection's `webhook_signing_key` within `webhookSignatureTolerance` of the clock, and accepts bodies up to `webhookMaxBodyBytes`. It answers `400` for a forged, stale, or malformed delivery, `413` for an oversized one, `405` for another method, `200` for another webhook event, such as `routing_form_submission.created`, and `503` while no binding runs, while the signing key is blank or credentials are unavailable, or when the inbox cannot record, so Calendly retries.
- The event ID is the webhook event followed by the scheduled event and invitee IDs, such as `invitee.created:EVENT0001:INVITEE01`, so a redelivery keeps its ID and starts no second Flow. A binding's `events` and `eventTypeUri` configuration filter what it records; the application's filter remains its admission rule.
- `newInviteeEventReceivedTrigger` and `inviteeEventReceivedWebhookHandler(connection)` run a binding without a project inbox, and `defineInviteeEventReceivedTriggerBinding` declares a static binding with its `eventTypePicker` unit for Dex Web.

Run `npm run check` for conformance replay, package tests, typecheck, and lint. Run `DEX_FLOW_SERVICE_ADDRESS=<host:port> npm run test:integration` against a running Dex dev server. The invitee-recorder integration test runs the example against a real Dex Server with a local Calendly API stand-in and locally signed deliveries. Live Calendly authorization, token refresh, API calls, webhook registration, and live webhook deliveries remain unverified.
